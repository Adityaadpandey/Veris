Headless Bluetooth
Shutter Trigger + Phone Tethering

Trigger photo capture from a paired Android phone over classic Bluetooth, and use the same phone's mobile data (Bluetooth PAN) for upload/sign/claim — for Pi deployments with no screen at all.

01

Goals & Non-Goals

GOALS What this delivers
  • Trigger a capture from an Android phone over Bluetooth — no touchscreen involved.
  • Use the phone's mobile data (Bluetooth PAN tethering) for upload/sign/claim, only when needed.
  • Stream capture/sign/upload progress back to the phone live.
  • Don't break or duplicate logic for existing touchscreen deployments.
NON-GOALS Explicitly out of scope
  • No BLE — classic RFCOMM/SPP for both trigger and PAN tethering (one consistent stack).
  • No phone-side viewfinder/live preview (stream_server.py exists separately, not part of this).
  • No gallery, mode switches, or other GUI features — trigger + status only.
  • No custom pairing UI — pairing & tethering are one-time manual OS steps.
02

03

Components

Three new modules plus one new entrypoint. The shared pipeline has no Kivy import — the only behavior change is swapping Clock.schedule_once UI calls for a status_callback(message, level) argument.

capture_pipeline.py — new, shared, no Kivy import
CameraController (moved as-is), sign_image() (from _sign_image), get_location(), upload_and_create_claim() (from _upload_and_create_claim, enqueues to retry queue on failure instead of just reporting), retry_pending_uploads(). Kivy's take_photo/_upload_and_create_claim/_sign_image become thin wrappers passing a status_callback that does the existing Clock.schedule_once UI work.
bt_trigger_server.py — new
Classic RFCOMM/SPP server (PyBluez or stdlib bluetooth). Advertises the standard SPP UUID under a fixed name (Veris-Cam-<device-id>). Accept loop serves one phone at a time and returns to listening on disconnect. Parses newline-delimited commands (v1: CAPTURE only). Exposes send_status(line) for the pipeline's status_callback.
bt_tether.py — new
Thin wrapper around Bluetooth PAN (BNEP). ensure_link(phone_mac, timeout=10) checks whether bnep0 already has an IP; if not runs bt-pan client <phone-mac> and polls for a DHCP lease up to timeout seconds. Returns True/False; upload treats False as "still offline" and falls back to the retry queue.
headless_camera_app.py — new entrypoint
Starts the trigger server's accept loop in a background thread; runs retry_pending_uploads() once at startup and on a periodic timer. On CAPTURE, runs capture → sign → upload via the shared pipeline, streaming status over RFCOMM. Ships as a systemd service analogous to lensmint.service.
pending/ retry queue — on-disk
One JSON file per queued upload (image path + signature info + camera id), next to CAPTURE_DIR. Written when upload_and_create_claim can't reach BACKEND_URL; drained by retry_pending_uploads(). Each success removes its file; push over RFCOMM is best-effort only.
04

Data Flow

Happy path end-to-end, then the offline fallback and auto-retry.

One-time setup
Pair the phone with the Pi (bluetoothctl on the Pi, standard flow on phone) and turn on the phone's Bluetooth tethering toggle.
RN app connects
Opens an RFCOMM socket to the Pi (fixed SPP UUID, Pi discoverable by fixed device name).
Shutter tap
User taps shutter → sends CAPTURE\n.
Pi pipeline
Captures, signs, brings up the PAN link if not already up, uploads, and streams status lines back live.
RN shows progress
Live progress; on UPLOADED:<claimUrl>, shows the claim URL/QR for minting.
Offline fallback
If the tether attempt times out, the photo is queued and the phone sees QUEUED:offline; the Pi retries automatically once a link is available — no second CAPTURE needed.

05

Status Vocabulary

Newline-delimited status strings streamed from the Pi to the phone.

CAPTURINGCamera capture in progress
CAPTUREDPhoto captured successfully
SIGNEDHardware signature applied
TETHERINGBringing up Bluetooth PAN link
UPLOADINGUploading to Filecoin / signing / claiming
UPLOADED:<claimUrl>Success — claim URL/QR shown
QUEUED:offlineSaved locally, will auto-retry
FAILED:<stage>Failure at capture, signing, etc.
06

React Native App Requirements

Library

react-native-bluetooth-classic (Android RFCOMM support).

Connect

Find the paired device by fixed name, connect to SPP UUID 00001101-0000-1000-8000-00805F9B34FB.

Trigger

Send CAPTURE\n on shutter tap; read newline-delimited status and reflect per vocabulary.

Connection state

Track socket state independently; show "not connected" and reconnect after drops (the Pi server always returns to accepting).

07

Error Handling

ScenarioPi behaviorPhone sees
No phone connected RFCOMM server just waits (nothing to do). Own socket state drives "not connected" UI.
Capture failure Reports stage capture. FAILED:capture
Signing failure Reports stage signing. FAILED:signing
No internet within tether timeout Photo + signature queued to disk; auto-retries later. QUEUED:offline
Upload failure after successful tether (backend error, non-200) Same queue-and-retry path as offline case. QUEUED:offline
08

Testing

MANUAL Hardware-in-the-loop
  • Pair a Pi + Android phone, enable phone Bluetooth tethering.
  • Use a generic Android "Bluetooth terminal" app to send CAPTURE and verify the status sequence and an actual upload/claim — before the RN app exists.
E2E Through the RN app
  • Normal trigger.
  • Trigger with phone tethering off (verify queue + later auto-retry).
  • Reconnect after drop.
ℹ
No screen on the target device — all verification is via the phone or by SSHing into the Pi and tailing the service logs.

Open Items & Follow-ups

Explicitly out of scope for this iteration — noted for later decisions.

ItemNote
Live preview from phone Would reuse stream_server.py over the PAN link, or a future BLE/WiFi path — not part of this change.
Multiple paired phones / access control v1 assumes a single trusted phone on the RFCOMM server.
iOS support Classic Bluetooth RFCOMM isn't available to third-party iOS apps; needs a BLE GATT redesign if iOS is ever required.
⚠
Key architectural risk to review: single trusted phone + fixed device name means no authentication on the RFCOMM server. Any paired device that knows the name could trigger captures. Worth confirming this matches the intended deployment threat model.
